# Qwen3.8-Flash-Next 125B-A6B 4-bit — v2 baseline telemetry

First baseline recorded against tag `v2` (commit `808cea3`), for optimising
decode. Nothing here is a release artifact; it is the "before" picture.

## Conditions

- Machine: Mac15,3 (M3) 24 GB, macOS 27.0, Swift 6.4; as idle as possible
  (`dasd` 0.0%, load ~1.9, no other model process).
- Model: `models/qwen3.8-flash-next_125B_A6B_4Bit` (3.2 GB `model_weights.bin`,
  63 GB `packed_experts`, 95 GB `ngram_table.bin`).
- Prompt: `difference swift vs c++ in detail`; `--max-new 256 --temperature 0`.
- Durable record: `benchmark/internal-speeds/v2-qwen38-4bit.json`.

## Reading it

- **59% of the span is not GPU work** (66.17 s span against 27.39 s busy) — the
  idle budget the CPU-core and I/O plans are aimed at.
- **`attn_norm_qkv` is the single largest GPU item** (10.9 s, 40% of busy) at
  12,240 calls — 47.8 per token, i.e. one per layer across the 48 layers —
  which is 42.5 ms of every token.
- **`head_logits` costs 13.5 ms/token** for 255 calls — the 8-bit head GEMV is
  the largest per-call cost in the profile.
- The MoE miss path (`moe_phase1_miss_fixup_phase2`, 5.0 s) plus the hit path
  (3.3 s) plus routed (1.5 s) is the expert half of the token.
- Prefill is negligible on a 7-token prompt (2.49 s is mostly first-touch and
  head); a coding-length prompt is a different measurement
  (`docs/qwen38-prefill-profile.md`).

Captured by launching `tools/server_launcher.sh server full qwen38 4 default off`
with `TINYTITAN_RUNNER_STATS=1 TINYTITAN_KERNEL_STATS=1` and posting the prompt to
`/v1/chat/completions`. **Post by the 125B's own id** — `/v1/models` is
catalogue-ordered, and posting to `data[0]` makes the on-demand switcher load the
4B instead.

| `expert_evictions` | 32,628 | heavy churn in the 96-slot cache |
| `expert_reloads` | 23,811 | **67% of misses re-read an expert the cache once held** |
| `expert_read_mib` | 94,270 (92 GB) | 368 MB/token; ≈1.44 GB/s average against a ~3.6 GB/s SSD |
| `io_ms` | 113.3 | expert I/O per token |

| `io_hidden_pct` | **12.13%** | only an eighth of miss I/O is hidden |
| `rdadvise_ms` / `rdadvise_mib` | 13.5 / 84,740 | advice traffic ≈ the reads themselves |
| `expert_load_p50/p95/p99` | 4 / 8 / 8 ms | SSD latency |
| `prefetch_issued_per_token` | **0.00** | prefetch ring is off |
| `early_hit_layers` | 0 | `early_hits=false` |
| `head_ms` | 12.7 | 8-bit head GEMV per token |
| `body_ms` / `cb1_ms` / `cb2_ms` | 225.4 / 4.4 / 1.1 | per token |
| occupancy / busy | **39.5%** / 102.9 ms per token | `span_ms=66,630` |

### What this gives the optimisation plans

- **I/O is the biggest single lever**: 90.5 ms/token of exposed wait, only 12% of
  miss I/O hidden, and two thirds of all misses are **reloads** — so retention and
  scheduling matter more than prediction depth for this model.
- **The prefetch ring is off** (`prefetch=0`, `prefetch_issued_per_token=0`), so
  the prefetch lever is genuinely untapped here rather than already spent.
- **The SSD is not saturated** (≈1.44 GB/s average of ~3.6 GB/s), which is what
  makes CPU-side staging and CPU expert computation plausible rather than
  bandwidth-starved.
- CPU compute headroom: 102.9 ms of GPU busy per token against ~59% idle span,
  and the CPU's own role in the token is small (the CLI breakdown shows the CPU
  turnaround only indirectly; the role table above is the GPU side).

## Noise floor (three baseline runs, same conditions)

Before any A/B, the baseline was repeated three times through the server path:

| run | decode tok/s | occupancy | busy ms/token | expert counters |
|---|---:|---:|---:|---|
| 1 | 4.062 | 41.3% | 108.6 | bit-identical |
| 2 | 4.071 | 41.0% | 107.3 | bit-identical |
| 3 | 4.132 | 40.1% | 103.5 | bit-identical |

Spread 0.07 tok/s. The routing is deterministic at temperature 0, so the expert
counters (hit rate 0.7167, 23,811 reloads, 94,270 MiB read) are identical across
runs and only wall-clock moves. That makes a 0.1 tok/s difference readable, and
any arm that *changes the counters* has changed the work, not just the timing.

### The shipped default, re-recorded

With the row at depth 1, `internal-speeds` was run again on the same 7-token
prompt and 256 new tokens (`benchmark/internal-speeds/v2-qwen38-4bit-prefetch-default.json`;
the first sample was taken while the promotion was still uncommitted and is what

| field | pre-change baseline | shipped default |
|---|---:|---:|
| decode | 3.993 tok/s | **4.676 / 4.538** |
| TTFT | 3.12 s | 2.39 / 2.63 s |
| response | `9cf91578…`, 901 chars | `3619d939…`, 1,070 chars (both runs) |

The 0.14 tok/s spread between the two default runs is wider than the 0.07

(server A/B 4.551 / 4.463); the size of the gain is not in doubt at either
sample. One side effect to read correctly: `gpu.routed_moe_gbps` reads 46.3

changed, not the kernel — decode is 13.6% faster and the same kernel's share of
a shorter token moved — so that per-kernel bandwidth is not comparable across
the two arms the way the comparator assumes.

Provenance, because the A/Bs straddle a deliberate numerics change and their
hashes are therefore not all comparable. The short-prompt A/B records

on a later binary and has no stored baseline for its own prompt, so what it
establishes is that its two arms produced byte-identical text (`051f5536…`, both
arms and both runs). The shipped default records `3619d939…`; that difference is
the instruct-row presence penalty, not prefetch — the same binary with

## Lever 2 — expert read advice and read submission (measured, left unchanged)

Two decode-side knobs had never been A/B'd on this engine:
`TINYTITAN_RDADVISE_POLICY=off` and `TINYTITAN_EXPERT_IO_SUBMISSION=immediate`.
Every arm of every sweep below returned the same response (`2087738fce…`), so
both are output-invariant. Short prompt, 256 tokens, temperature 0.

| arm | runs (tok/s) | paired mean | positive |
| --- | --- | ---: | ---: |
| base | 4.495 / 4.481 / 4.543 / 4.593 / 4.577 / 4.478 / 4.596 / 4.509 | — | — |
| rdadvise off | 4.645 / 4.647 / 4.598 / 4.618 / 4.607 / 4.612 / 4.533 | **+0.053 (+1.15%)** | 4/4 |
| submission immediate | 4.623 / 4.677 / 4.545 / 4.638 / 4.588 / 4.624 | **+0.059 (+1.29%)** | 3/4 |
| `EXPERT_IO_SYNC=event` | 3.961 | **-0.534 (-11.9%)** | — |

The last four base samples against the last four of each arm are one
interleaved pass (four rounds of base/rd-off/immediate), which is what the
paired column quotes: the unpaired base drifted 4.478-4.596 (2.6%) across the
session, more than either effect, so only the paired differences carry weight.
`sync=event` stays off for the same reason the wiki says it is the comparison
path, not the fast one: it triples `wait_ms`.

**Why the advice is dead work rather than I/O.** The streamer advises on its own
plain descriptor while the reads go through a separate `F_NOCACHE` reader, so
the advice warms a page cache the demand path never reads. It is issued once per
missed expert (26,797 calls for this 256-token run) and the co-execution plan's
idle budget already books `rdadvise` at 1.0 ms/token. Sampling `iostat -d disk0 1`
during generation settles what it does *not* do: every arm reads 108.6-109.4 GiB
off the device for ~80.7 GiB of demand expert reads (ratio 1.35, constant), so
the advice adds no device traffic at all. Its whole cost is syscall and
scheduling work, which is why removing it is worth about a percent.

**Neither default was changed, because the sign is family-dependent.** The same
paired design on Qwen 3.6 35B-A3B 4-bit (`qwen3.6-35b-a3b_4-Bit`, the same
`deferred`/`default` shipped settings) reverses:

| arm | round 1 | round 2 |
| --- | ---: | ---: |
| base | 17.466 | 17.441 |
| rdadvise off | 16.873 (-3.4%) | 12.046 (-31%, contaminated: identical counters, +6.6 s wall) |
| submission immediate | 16.869 (-3.4%) | 16.807 (-3.6%) |

That confirms `docs/v4.2-expert-streaming-engine.md`'s reason for leaving
submission deferred ("immediate submission was slower in the representative
real-model A/B") on the family it was measured against. A global flip would
therefore trade ~+1% on Qwen3.8 for ~-3.5% on Qwen3.6, and capturing the Qwen3.8
side would need a per-profile field with its own cross-family evidence — not
worth a ~1% effect at the edge of resolution. What is settled is that the two
are nested rather than additive: advice is only issued on the deferred path
(`plannedLoad == nil`), so `immediate` already skips it, and the combined arm
measured +1.40%, inside the noise of either alone.

## Lever 3 — the cache ceiling is not costing decode here (measured, kept)

`RuntimeConfiguration.affordableExpertCacheBudget` clamps the profile's 12 GiB
tune to a third of physical memory, which on this 24 GiB machine is 8 GiB — 64
slots rather than the 96 the row asks for. The clamp's own comment calls a
conditional ceiling "the obvious next experiment", and the 2026-09-20 port
recorded a 1.3% decode price for it on Qwen 3.6 4-bit. On Qwen3.8 4-bit the
sign is the opposite, in every paired round:

| round | shipped (64 slots) | `TINYTITAN_EXPERT_CACHE_SLOTS=96` | delta |
| --- | ---: | ---: | ---: |
| 1 | 4.613 | 4.343 | -0.270 |
| 2 | 4.905 | 3.955 | -0.950 |
| 3 | 4.573 | 3.831 | -0.742 |

Mean **-0.654 tok/s (-14%)**, 0/3 positive, same prompt and shape as every other
sweep here. The counters say the bigger cache does exactly what it is for — hit
rate 0.757 -> 0.827 and expert read 80.7 -> 57.6 GiB per run — and the token
still gets slower. So on this engine the cost is not read volume: 4 GiB more
wired cache (12 GiB against 8 GiB) and a longer slot search cost more than the
23 GiB of demand reads they save, with the prefetch ring already converting
misses into hits.

The swap caveat this first carried is now closed. Re-run later the same day with
swap sampled per arm and much lower pressure (3.3-3.4 GB against 4.18 GB), the
tuned cache loses again in all three paired rounds: 4.521/4.132, 5.004/4.136,
4.964/4.065 — mean **-0.719 tok/s (-15.6%)**, 0/3. So on this machine the clamp
is not merely protective, it is the faster setting by a wide margin, and the
tuned-96-slot arm is remarkably stable (3.83-4.34 tok/s across six samples). The
conditional-ceiling experiment stays closed; the long-prompt variant of this A/B
is the only version not run.

## Lever 4 — the page-cache path (measured; a documented trade, not a new default)

`TINYTITAN_BOUNDED_IO=0` opts out of the `F_NOCACHE` expert reader, so slot
misses are served by plain preads and the unified buffer cache can hold expert
data. The streamer's own comment records what the shipped default pays for a
declared footprint: "15-30% of decode throughput" on the engine that measured it.
On this engine, paired and interleaved on the same short prompt:

| round | shipped (bounded) | page cache | delta |
| --- | ---: | ---: | ---: |
| 1 | 4.414 | 4.727 | +0.313 |
| 2 | 4.481 | 4.765 | +0.284 |
| 3 | 4.444 | 4.560 | +0.116 |

Mean **+0.238 tok/s (+5.4%)**, 3/3 positive, response identical
(`2087738fce…`). `io_ms` falls 94-100 -> 86-89 while the miss counters do not
move (80.9 GiB of requested reads in both), so the page cache is serving slot
misses the counters still count. Swap did not grow during the sweep (3.6 -> 3.5
GB used), so the trade costs undeclared memory headroom rather than paging over a
three-minute window.

The ~500-token prompt confirms the sign with more scatter: 3.977 -> 4.261
(+7.1%) and 4.064 -> 4.090 (+0.6%), mean +0.155 (**+3.9%**), 2/2 positive, the
same response (`051f5536…`). The scatter is the machine's rather than the
trade's — the shipped arm itself moved 3.977 -> 4.064 between rounds — so across
both prompt lengths the honest number is **+4-5% decode**.

The same sweep closes the advice question from the other side. Inside the
page-cache path, `TINYTITAN_RDADVISE_POLICY=off` measures **+3.5%** against the
shipped path but ~1.8% *below* the page-cache arm with advice on: advice earns
its keep exactly where the reads can consume it. With Lever 2 (advice adds no
device traffic under bounded I/O) that is the whole picture — dead work when the
reads bypass the cache, useful when they use it.

**Prefill does not benefit, and that is the same fact as the layer-major ceiling.**
The same trade on the 9,000-token prompt, two paired rounds:

| round | shipped prefill | page cache | occupancy shipped / page cache |
| --- | ---: | ---: | --- |
| 1 | 385.8 s | 389.2 s | 90.1% / 88.9% |
| 2 | 384.0 s | 391.1 s | 89.7% / 88.9% |

No gain (0/2; the page-cache arm is 1.4% slower on the mean). Prefill's expert
reads are already ~90% overlapped with GPU work, so there is no exposed I/O for a
page cache to serve — which is the same 90% occupancy that bounds the layer-major
line at ~10% (see `docs/qwen38-layer-major-prefill.md`). The page-cache arm's swap
also grew 712 MB in round 2 (3.49 -> 4.21 GB), against a flat/falling shipped arm,
so the prefill case is a memory cost with no throughput return.

**Not a default change, and now not an option either.** The shipped default is
deliberate: the page-cache path "borrows memory it never declares", which is the
property the streaming design exists to protect. **Decision 2026-09-21: the
opt-in is rejected outright — the RAM budget must remain enforced on every
machine — so the trade is not available regardless of its throughput.** Recorded
here so it is not re-proposed. The 15-30% figure predates the prefetch ring,
whose hit conversion is why the remaining page-cache benefit is smaller now.

## Lever 5 — the prefetch-quality family, re-measured with a working ring

The tier, lookahead and margin A/Bs that originally set these defaults all ran
while the prefetch ring was clogged. The 2026-09-05 profile says so itself: "the
tier and lookahead A/Bs, the 5.0.2 README table — ran with prefetch effectively
off." With the ring at its shipped depth 1, two paired rounds each and the same
short prompt, every alternative to the shipped configuration is a wash or a loss,
and every arm returned the same response (`2087738fce…`).

| arm | round 1 | round 2 | mean delta | issued / adopted per token |
| --- | ---: | ---: | ---: | --- |
| shipped (tier default, ahead 1, top-M 1, no gate) | 4.573 | 4.503 | — | 42.6 / 22.9 |
| `PREFETCH_IO_TIER=utility` | 4.472 | 4.591 | -0.14% (1/2) | 42.8 / 23.3 |
| `PREFETCH_IO_TIER=throttle` | 4.573 | 4.448 | -0.61% (0/2) | 42.6 / 22.9 |
| `PREFETCH_AHEAD=2` | 4.403 | 4.417 | -2.82% (0/2) | 43.8 / 19.0 |
| `PREFETCH_TOP_M=2` | 4.236 | 4.245 | **-6.56% (0/2)** | 76.1 / 16.3 |
| `PREFETCH_MIN_MARGIN=0.03` | 4.263 | 4.433 | -4.19% (0/2) | 23.4 / 16.6 |

The counters say why: depth 2 casts 76 speculative reads a token and *adopts
fewer* of them (16.3 against 22.9), and the margin gate filters so hard that it
loses adoptions too (16.6). One read deep, ungated, on the default I/O tier is
the optimum — and that is now a measurement rather than a verdict inherited from
a dead mechanism.

## Lever 6 — the retention family, same re-measurement

Same treatment for the four knobs whose verdicts were also inherited from the
clogged-ring session. Two paired rounds each, short prompt:

| arm | round 1 | round 2 | mean delta | hit rate |
| --- | ---: | ---: | ---: | ---: |
| shipped (early hits off, per-slot, LFU, wired) | 4.369 | 4.620 | — | 0.758 |
| `EARLY_HITS=1` (also selects gpuResidency + pooled layout) | 4.613 | 4.576 | +2.22% (1/2) | 0.756 |
| `EXPERT_CACHE_LAYOUT=pool` | 4.528 | 4.394 | -0.75% (1/2) | 0.757 |
| `EXPERT_CACHE_POLICY=lru` | 4.651 | 4.530 | +2.14% (1/2) | 0.762 |
| `KEEP_WIRED=0` | 4.646 | 4.310 | -0.37% (1/2) | 0.756 |

Every arm is 1/2 positive and every mean is smaller than its own round-to-round
swing — the shipped arm itself moved 4.369 -> 4.620, 5.7%, between rounds — so
all four are washes on this prompt: the shipped choices are not leaving anything
readable on the table. Settling a 1-2% effect here would take more pairs, not a
different knob, and none of these promises more than that. Every arm returned
`2087738fce…`, and `early_hit_layers` moved 0 -> 12,240 when early hits were on,
so the arms really did take their paths.

The last I/O knob, `TINYTITAN_PARALLEL_IO=0` (shipped on), is a wash as well:
+0.033 / +0.052 / -0.029 against base, mean **+0.019 tok/s (+0.4%)**, 2/3 — with
the prefetch ring and a 64-slot cache there are rarely several misses in one plan
for parallel fills to matter. No change.

That completes the knob inventory for this model on this machine: every tunable
in the decode and prefill paths now has a measurement taken with the current
engine, and the shipped configuration is the measured optimum of every family
except the page-cache opt-in (+4-5% decode, undeclared footprint).

| 6 GB | 48 | 3.967 | 4.2 | 98,429 | 0.704 | 90 | 119.1 | 11.6% | 41,653 / 31,913 |
| 8 GB | 64 | **4.547** | 4.3 | 80,793 | 0.757 | 84 | 97.2 | 13.6% | 33,434 / 24,462 |
| 10 GB | 64 | **4.599** | 4.3 | 80,642 | 0.758 | 84 | 95.7 | 13.7% | 33,434 / 24,462 |
| 12 GB | 96 | 4.000 | 4.8 | 57,465 | 0.827 | 141 | 68.1 | 32.9% | 21,849 / 14,413 |
| 16 GB | 128 | 2.260 | 4.9 | 44,510 | 0.866 | 297 | 80.2 | 38.8% | 14,098 / 8,183 |

Every successful arm returned the same response (`2087738fce…`, 1,223 chars), so
budget changes the schedule only.

- **1 GB is not slow, it is unusable.** Generation fails with "expert cache
  cannot place requested experts: 10 experts do not fit in 8 cache slots (policy
  lfu, avoiding 0 slots)" — the model routes top-10, so a budget must afford at
  least 10 slots per layer, and the 8-slot rung cannot. The practical floor is
  2 GB / 16 slots.
- **The optimum is 64 slots, and the shipped clamp is already there.** 8 GB and
  10 GB both resolve to 64 slots, and their counters are bit-identical (same
  evictions, same reloads) with decode within 1.1% — which is both a drift check
  and a confirmation of the slot arithmetic.
- **Past 64 slots the curve falls while the counters improve**: hit rate
  0.757 -> 0.827 -> 0.866 and reads 80.8 -> 57.5 -> 44.5 GiB, but decode
  4.60 -> 4.00 -> 2.26 tok/s and `wait_ms` 84 -> 141 -> 297. The bigger cache
  hides more of the wait and still loses, and at 16 GB the machine also swapped
  2.8 GB during the run (3.7 -> 6.6 GB). This is the same wait effect Lever 3
  measured, now across the whole curve: bytes are not the constraint.
- **Prefill is flat** (4.2-4.9 s) across every budget, which is the prefill
  cache being inert (Lever 3's other half).

Single run per budget; the curve's shape is far outside the machine's scatter,
but treat any single point as +/-10%.

## Lever 8 — the prefetch slot allocation (measured; no change)

The shipped ring is one speculative read a layer, the first non-resident expert in
the probe's rank order. Two slots can spend the second read on L+1's next
non-resident expert or on L+2's; the far read has an extra layer to land in, and
round 1 of `docs/qwen38-prefetch-predictor-study.md` showed the second rank mostly
arriving too late to be adopted. The mixed-horizon arm was an experiment patch,
measured below and then reverted — the tree carries no losing knob. Two interleaved
rounds, short prompt, `--ram 8`, binary `d9e1a084…`:

| arm | r1 / r2 | delta | issued / adopted per token | demand MiB/token | io_ms |
| --- | --- | ---: | --- | ---: | ---: |
| shipped (near rank order, 1 read) | 4.570 / 4.548 | — | 42.7 / 23.3 | 315.0 | 95.6 |
| mixed horizon (near + far, patch) | 4.509 / 4.477 | -1.4% | 58.7 / 24.8 | 311.0 | 96.8 |
| two ranks of L+1, per-expert | 4.481 / 4.514 | -1.3% | 76.2 / 26.2 | 307.3 | 99.3 |

Demand bytes fall in both wider arms and `io_ms` rises — demand throughput
3.30 → 3.09 GB/s — so the extra speculative read is charged against the demand
reads rather than hidden in idle device time. `spec_load_ms` rises with the ring
width (1.16 / 1.59 / 1.74), and an adopted read is only worth 2.64 MiB = 0.80 ms
against a 1.16 ms read. **42.7 reads a token is where the device's idle window is
full.** All arms returned `2087738fce…`; the shipped path is byte-identical and
unchanged. `TINYTITAN_PREFETCH_PER_EXPERT=1` is still in the tree from Lever 5's
session and is the one arm of the three that remains runnable.

## Lever 9 — the losing knobs are gone (2026-09-22)

Every switch in Levers 1-8 that measured a wash or a loss has been deleted from
the engine, not merely left in its losing position. Removed:

| knob | verdict | what was deleted with it |
| --- | --- | --- |
| `TINYTITAN_PREFETCH_PER_EXPERT=1` | -2.0% / -3.3% | the per-expert operation path, back to one batch operation |
| `TINYTITAN_PREFETCH_AHEAD=2` | -2.8% | the two-layer-ahead prefetch feed (the probe-2 trace stays) |
| `TINYTITAN_PREFETCH_TOP_M` | -6.6% at 2, -9.8% at 4 | the depth override; the profile row's depth is the only source |
| `TINYTITAN_PREFETCH_MIN_MARGIN` | -4.2% | the expected-value gate |
| `TINYTITAN_PREFETCH_IO_TIER` | -0.1% / -0.6% | the ring's disk-tier plumbing, the profile tier field and the C `_tier` reader entry point |
| `TINYTITAN_EXPERT_CACHE_POLICY` | washes | aging-lfu, the decayed score and its half-life (lfu/lru stay as runtime configuration) |
| `TINYTITAN_CACHE_DECAY_HALFLIFE` | — | the decayed score's bookkeeping |
| `TINYTITAN_EXPERT_CACHE_LAYOUT` | -0.75% | the pooled layout and its `moe_phase1_gate_up_act_pool_u16load` kernel |
| `TINYTITAN_EARLY_HITS` | +2.2% (1/2) | the early-hit phase-1 path, its kernel selection and the pool handle |
| `TINYTITAN_KEEP_WIRED` | -0.37% | the tri-state override; the profile row decides |
| `TINYTITAN_PARALLEL_IO` | +0.4% (2/3) | the serial fill path; fills are always parallel |
| `TINYTITAN_PREFILL_LAYER_MAJOR` / `_SLOTS` | 2.7x slower | the whole layer-major schedule, its residual-per-chunk plumbing and the concentrated-slot override |

What remains is the measured optimum of each family, and the only two decode-side
switches left are on/off controls for wins: `TINYTITAN_PREDICTIVE_PREFETCH` and
`TINYTITAN_BOUNDED_IO=0` (which is faster but rejected by the RAM decision). The
shipped path is byte-identical to the one these measurements were taken on.
